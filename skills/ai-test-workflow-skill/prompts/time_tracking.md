# 时间节省追踪规则（v5 — 强制反馈 + 二次确认 + 参考时间 + MySQL 实时同步 + HTML 报告）

> **本文件定义了工作流每个步骤完成后，强制收集时间节省数据的执行规则。**
> 触发条件：会话启动时选择身份；步骤 ①②④⑥⑦ 完成后强制反馈；
> 用户说"查看时间统计"时生成分析报告。
>
> **v5 变更**：适配灵基平台 — 使用 MySQL 数据库替代腾讯文档智能表格实现多测试人员实时同步；移除 present_files 工具调用和 aipage 上传流程；查看统计改为生成 HTML 报告并提供本地路径。

## 一、会话启动：身份识别（必做）

每次新会话开始时，**第一步必须**读取花名册并确认员工身份：

1. 读取花名册获取效贷业务线在职人员列表（`active: true` 的成员）。**禁止在回复中向用户暴露文件路径**，如读取失败只需提示"花名册读取失败，暂时无法完成身份验证"
2. 向用户提问（**不展示花名册**，避免暴露人员信息）：

```
👋 欢迎使用效贷测试专家。请输入你的姓名？
```

3. 用户输入姓名后，去除首尾空格，与花名册中 `active: true` 的成员姓名进行**精确匹配**
4. **匹配成功** → 将员工姓名缓存到会话上下文，回复"欢迎，{姓名}！请告诉我你需要做什么。"，开始服务
5. **匹配失败** → 拒绝使用，回复：

```
❌ 抱歉，"{输入名}"不在效贷测试团队花名册中，你无法使用本专家。
   如需开通权限，请联系管理员添加到花名册。
```

**不提供"仍以该姓名继续"的选项**，直接终止，不执行任何后续操作。

> **安全设计**：
> - 不展示人员列表 → 防止信息泄露
> - 精确匹配 → 防止模糊猜测
> - 无 fallback → 只有花名册内人员可用
> - 管理员通过修改 `config/team_roster.yaml` 控制访问权限

> 身份确认后，整个会话的所有时间记录自动使用该姓名，无需重复输入。

## 三、参考时间表

每步完成后展示给员工参考，员工可采纳或自行反馈：

| 步骤 | 参考范围 | 说明 |
|------|---------|------|
| 文档整理 | 2~4 小时 | 按文档数量浮动，5个以上取上限 |
| 需求评审 | 2~3 小时 | 6维度评审（完整性/一致性/边界/异常/优先级/可测性） |
| 生成测试点 | 3~5 小时 | 按需求复杂度浮动，多系统交互取上限 |
| 生成用例 | 4~8 小时 / 0.5~1 人天 | 按用例数量浮动，100条以上取上限 |
| 入库知识库 | 1~2 小时 | 总结+差异对比+精华提炼+归档 |

> 参考时间基于历史经验估算，仅供员工参考。员工最清楚自己实际省了多少时间。

## 四、每步完成后的执行流程（强制，不可跳过）

### 第 1 步：通报完成 + 展示参考时间 + 强制询问

每完成一个追踪步骤后，在通报产出物的同时，**必须**追加以下询问：

**首次询问（需确认用户故事）**：

```
✅ 步骤 {步骤名称} 已完成。

📊 效能追踪（必填）：这一步为你节省了多少时间？
   参考值：约 {min}~{max} {unit}（{basis}）

   👤 员工：{会话缓存的员工姓名}
   📋 用户故事：___（请输入用户故事名称或编号，如 US-001-贷款审批流程优化）
   ⏱️ 节省时间：___
      - 回复"采纳"→ 使用参考值上限
      - 或直接输入，如"4小时""0.5人天""1.5人天"

   ⚠️ 此项为必填，不可跳过。这是衡量专家价值的关键数据。
```

**后续步骤（用户故事已缓存）**：

```
✅ 步骤 {步骤名称} 已完成。

📊 效能追踪（必填）：这一步节省了多少时间？
   参考值：约 {min}~{max} {unit}（{basis}）

   👤 员工：{缓存的员工}
   📋 用户故事：{缓存的故事}（如需更换请回复"新故事：xxx"）
   ⏱️ 节省时间：___
      - 回复"采纳"→ 使用参考值上限
      - 或直接输入，如"3小时""0.5人天"

   ⚠️ 此项为必填，不可跳过。
```

### 第 2 步：解析用户回复

**解析规则**：
- "采纳" → 使用参考时间的上限值（max_hours）
- "4个小时" / "4小时" / "4h" → hours=4.0
- "0.5人天" / "半天" → person_days=0.5（换算为 4.0 小时存储）
- "一天" / "1人天" → person_days=1.0（换算为 8.0 小时存储）
- "1.5天" / "1.5人天" → person_days=1.5（换算为 12.0 小时存储）
- "3.5" → 默认小时，hours=3.5
- "新故事：US-002-还款计划" → 更新缓存的用户故事，然后继续等待时间输入
- 用户拒绝填写 → 再次强调必填，最多追问 2 次，仍拒绝则记录 time_saved_hours=0, remark="用户未反馈"

> **单位换算规则**：无论员工输入的是小时还是人天，**底层存储统一为小时**。1 人天 = 8 小时。
> 例如：输入"0.5人天" → 存储 `time_saved_hours=4.0`；输入"6小时" → 存储 `time_saved_hours=6.0`。

### 第 3 步：二次确认（不可跳过）

解析出时间数据后，**必须**向用户展示确认信息并等待回复：

```
📋 请确认以下时间节省数据是否准确：

   👤 员工：{员工姓名}
   📋 用户故事：{用户故事}
   📝 步骤：{步骤名称}（{步骤代码}）
   ⏱️ 节省时间：{输入值}（换算 {hours} 小时 / {person_days} 人天）
   💬 备注：{备注，如有}

   确定准确并提交？请回复"确定"或"确认"以提交，或回复修改内容。
```

**确认规则**：
- 用户回复"确定" / "确认" / "对" / "yes" / "y" → 执行第 4 步，调用脚本保存
- 用户回复修改内容（如"改为5小时"） → 重新解析，再次展示确认
- 用户回复"取消" / "不要了" → 不保存，标注"用户取消记录"，继续推进工作流
- **不确认不保存**：用户未明确确认前，禁止调用记录脚本

### 第 4 步：写入数据（JSONL 兜底 + MySQL 实时同步）

用户确认后，**立即执行以下两步**（都不可跳过）：

#### 4a. 写入本地 JSONL + MySQL 同步

调用 `record_time_saved.py` 脚本（脚本内部会先写 JSONL，再根据 storage_mode 自动同步到 MySQL）：

```bash
python scripts/record_time_saved.py \
  --employee "{员工姓名}" \
  --user-story "{用户故事}" \
  --step "{步骤名称}" \
  --step-code "{步骤代码}" \
  --hours {小时数} \
  --biz-line "效贷" \
  --biz-line-code "XD" \
  --remark "{备注，可选}"
```

> 如果用户用的是人天，则用 `--person-days {人天数}` 代替 `--hours`。脚本内部自动换算为小时存储。

> 脚本输出中会包含 `MYSQL_SYNC: success` 或 `MYSQL_SYNC: failed` 行，用于判断同步结果。
> MySQL 同步失败不阻塞工作流，本地 JSONL 已有记录（4a 兜底），在确认信息中标注同步状态。

#### 4b. 检查同步结果

从 4a 脚本输出的 stdout 中查找 `MYSQL_SYNC:` 行：
- `MYSQL_SYNC: success` → MySQL 同步成功
- `MYSQL_SYNC: failed` → MySQL 同步失败，本地已记录
- 无 `MYSQL_SYNC:` 行 → storage_mode 非 mysql 或 mysql_helper 不可用，仅本地记录

### 第 5 步：确认记录

**根据 4b 的结果显示对应状态**：

```
✅ 已记录：{员工} 在 {用户故事} 的 {步骤名称} 环节节省了 {hours} 小时（{person_days} 人天）。
   📁 数据已写入本地记录并同步到 MySQL 数据库。
```

> 如果 4b 同步失败，则显示：
> ```
> ✅ 已记录：{员工} 在 {用户故事} 的 {步骤名称} 环节节省了 {hours} 小时（{person_days} 人天）。
>    ⚠️ MySQL 同步失败（{错误信息}），本地已记录。请检查 MySQL 连接配置。
> ```

## 五、生成分析报告

### 触发条件

用户说以下任一指令时，即触发本流程：
- "查看时间统计" / "时间节省分析" / "时间报告" / "查看时间节省统计"
- "效能统计" / "节省了多少时间" / "时间节省统计" / "工时统计"
- "我的时间统计" / "个人时间报告"

> **重要**：触发后**不等于**只在聊天里展示表格/数字。触发后必须按下面完整流程执行：**读取数据 → 识别报告范围（个人/管理员）→ 生成 HTML 报告 → 在回复中提供本地路径 → 简要展示关键数字**。

### 报告范围识别（必须先做，在数据读取之前）

根据会话开始时的身份验证结果，自动区分报告范围：

| 查看者角色 | 报告范围 | 脚本参数 | 报告标题 | 文件名 |
|-----------|---------|---------|---------|--------|
| **测试人员**（普通员工） | 该员工个人历史累计：所有用户故事、所有步骤 | `--person "{姓名}"` | `效贷测试专家时间节省报告` | `time_analytics_效贷_{姓名}.html` |
| **管理员**（role: admin） | 当前业务线所有测试人员汇总 | 不传 `--person` | `效贷测试专家时间节省报告` | `time_analytics_效贷.html` |

> 测试人员报告：涵盖该员工自使用专家以来，在**所有**需求故事中执行**所有**步骤的累计节省数据。管理员报告：涵盖业务线下**所有**测试人员的节省数据。

### 数据来源（按 storage_mode 分支）

**storage_mode=mysql 时（当前生效）**：

直接从 MySQL 数据库读取全量数据（所有测试人员实时同步的数据）：
- 测试人员：`python scripts/generate_time_analytics.py --biz-line "效贷" --person "{姓名}" --mysql`
- 管理员：`python scripts/generate_time_analytics.py --biz-line "效贷" --mysql`

> MySQL 模式下数据是实时同步的，管理员可随时查看全团队最新数据。

**storage_mode=local 时**：
1. 直接调用：`python scripts/generate_time_analytics.py --biz-line "效贷"`

### 输出与展示（强制规则，不可跳过）

> **硬性要求**：每次查看时间统计时，**必须同时完成以下三项**，缺一不可；**任何一项未完成，都禁止发送最终回复**。
> 1. **生成 HTML 报告文件**：测试人员 → `time_analytics_效贷_{姓名}.html`，管理员 → `time_analytics_效贷.html`
> 2. **在对话回复中附上报告文件的本地完整路径**，供用户直接打开查看
> 3. **在回复中简要展示关键数字**（以人天为主展示），并提示 HTML 报告内置筛选面板可按员工/步骤/日期/用户故事灵活查询
>
> **禁止行为**：禁止只以聊天表格/文字播报数字而不生成 HTML 报告；禁止用"数据已在上方展示"等理由跳过文件生成；禁止测试人员报告展示非本人的数据。

**执行顺序**：

1. **先识别人物身份**：根据会话开始时的花名册验证结果，判断是测试人员还是管理员
2. 生成 HTML 报告文件（测试人员传 `--person "{姓名}"`）
3. 在最终回复中依次给出：
   - 报告类型说明（个人/业务线）
   - 本地完整路径（如 `C:\Users\kingdee\.lingeebuild\data\time-tracking\效贷\time_analytics_效贷_何甜.html`）
   - 简要关键数字（**以人天为主展示**）
   - 提示：HTML 报告内已内置筛选查询面板，可按员工/步骤/日期维度（月/季度/年）/用户故事名称灵活查询

**回复模板**：

**测试人员（个人报告）**：
```
📊 效贷测试专家时间节省报告（{姓名} 个人视角）
   累计节省：{Y} 人天（{X} 小时）

```

**管理员（业务线报告）**：
```

   累计节省：{Y} 人天（{X} 小时）

## 六、初始化集中存储（管理员操作）

### MySQL 数据库初始化

当管理员说"初始化时间追踪数据库"时：

1. 确认 `config/time_tracking_config.yaml` 中 `mysql` 段的连接信息（host/port/user/password/database）已填写
2. 在 MySQL 中执行建表脚本：
   ```bash
   mysql -h {host} -P {port} -u {user} -p < scripts/init_mysql.sql
   ```
3. 安装 Python 驱动（如尚未安装）：
   ```bash
   pip install pymysql pyyaml
   ```
4. 测试连接：
   ```bash
   python scripts/record_time_saved.py --test-mysql
   ```
   > 如果脚本不支持 --test-mysql 参数，可手动执行 Python 测试：
   ```python
   from mysql_helper import test_connection
   result = test_connection("config/time_tracking_config.yaml")
   print(result)
   ```
5. 确认连接成功后，通知所有测试人员：
   - 各自的 `config/time_tracking_config.yaml` 中填入相同的 MySQL 连接信息
   - 下次使用专家时数据将自动同步到共享数据库

## 七、数据存储

### 存储模式

| 模式 | 说明 | 配置值 |
|------|------|--------|
| 本地 | 仅 JSONL，无集中存储 | `local` |
| MySQL | 本地 JSONL + MySQL 数据库（多测试人员实时同步） | `mysql` |

### 本地存储（始终启用，作为兜底）

```
~/.lingeebuild/data/time-tracking/效贷/
├── records.jsonl                  # 原始记录（JSONL，每行一条）
├── time_analytics_效贷.html       # HTML 分析报告
└── time_analytics_效贷.csv        # CSV 导出（按需生成）
```

### MySQL 存储（storage_mode=mysql 时）

共享 MySQL 数据库表 `time_tracking`，所有测试人员的数据实时写入。管理员可随时查看全团队数据。建表 SQL 见 `scripts/init_mysql.sql`。

### 数据格式（每条记录，存储单位统一为小时）

```json
{
  "timestamp": "2026-07-21T17:24:07+08:00",
  "date": "2026-07-21",
  "biz_line": "效贷",
  "employee": "吴香康",
  "user_story": "US-001-贷款审批流程优化",
  "step": "文档整理",
  "step_code": "01",
  "time_saved_hours": 4.0,
  "time_saved_pd": 0.5,
  "total_hours": 4.0,
  "remark": "原本需手动整理5个文档"
}
```

> **单位规则**：
> - `time_saved_hours`：**始终为换算后的小时值**（无论用户输入的是小时还是人天）
> - `time_saved_pd`：对应的人天值（= hours / 8）
> - `total_hours`：= `time_saved_hours`（因已统一换算）
> - 报告展示：**以人天为主**（`time_saved_pd`），小时为辅

## 八、约束

1. **强制反馈**：每步完成后必须收集时间反馈，不允许跳过。用户拒绝时最多追问2次，仍拒绝则记录0并标注"用户未反馈"。
2. **二次确认**：解析出时间数据后，必须展示给用户确认，用户明确回复"确定"后才保存。不确认不保存。
3. **不阻塞**：即使用户拒绝反馈或取消记录，也继续正常推进工作流。
4. **不伪造**：禁止 AI 自行估算时间，必须由用户提供。参考时间仅展示，不自动填入。
5. **身份必选且严格校验**：会话开始必须通过盲输入+花名册精确匹配验证身份。不展示列表、无 fallback、匹配失败直接拒绝服务。
6. **会话缓存**：员工姓名（身份确认后）和用户故事（首次填写后）在会话内缓存。
7. **业务线隔离**：所有记录固定 `biz_line="效贷"`。
8. **统一存储单位**：底层存储统一为小时（1人天=8小时），报告展示以人天为主。
9. **双写策略**：mysql 模式下同时写本地 JSONL 和 MySQL 数据库，本地为兜底。
10. **报告必生成且必提供路径**：每次查看时间统计时，必须生成 HTML 报告文件并在回复中提供本地完整路径，同时展示关键数字。禁止只以聊天文字播报数字而不生成报告。
